The Gizmoduck Plugin: Technical Reference

Generated from useful-claude-add-ons@541b2b70 on 2026-09-22. Verify before trusting.
The low-level guide, for the people who install, run and extend gizmoduck. A companion overview covers the same ground in plain language. Written against gizmoduck 0.5.3, commit 541b2b70.

Scope. Gizmoduck runs Nuclei (MIT-licensed, self-hosted) end to end — scan, normalise, report, ticket, diff — with no export step and no third-party API in the loop. Runs on WSL/Linux and Windows.

argparse runs with allow_abbrev=False, so --yes must be spelled out in full — an abbreviation cannot trip the ticketing gate by accident. --yes is refused with a named error on every subcommand except tickets, rather than being silently ignored.

3. The Ticketing Gate

cmd_tickets computes a digest over the exact record set (_records_digest) and requires it back, verbatim, on --yes:

  • No --yes: prints one line per candidate ticket (severity + subject), the digest, and the exact rerun command carrying it; exits 3 with GIZMODUCK_CONFIRMATION_REQUIRED and no JSON.
  • --yes present but not equal to the freshly recomputed digest: exits 3 with GIZMODUCK_APPROVAL_MISMATCH — a different findings file, a different --min-severity, or findings that changed in between all produce this.
  • --yes matching: emits the JSON ticket records for the caller (the /gizmoduck:scan and /gizmoduck:tickets command prose) to act on.

The severity floor for tickets defaults to High rather than the CLI-wide Info default, specifically so a bare invocation cannot open a ticket per informational finding.

4. Severity Model

SEV_NUM (gizmoduck.py:38, mirrored in normalize.py with a parity note): critical=4, high=3, medium=2, low=1, info=0, unknown=0. normalize.py maps a handful of legacy tool vocabularies onto this scale (Bridgecrew's "moderate"/"important", ZAP's numeric riskcode 0-3) and reports anything it cannot map as unknown rather than guessing a severity for it.

5. The Routine Orchestrator (Not yet a Command)

scripts/routine.py implements a manifest-driven, multi-tool scan (run_routine), each of the nine adapters conforming to one contract: run(location, outdir, opts) -> (raw_path | None, ToolResult) and parse(raw_path, name) -> list[dict], called with plain strings rather than a Target object. result.returncode is None means an adapter declined to run an active scan before firing anything (currently only sqlmap's active mode) — reported as skipped-active, never as an error. doctor already surfaces every adapter's availability under -- scanners --, driven off the same registry, so a tool added to scanners/ can never go unmentioned there — but as of this commit nothing in commands/ or skills/gizmoduck/SKILL.md calls run_routine; the only exercised path into it is scripts/_test/.

7. Known Items

  • The nine-tool routine.py orchestrator has no slash command or skill entry point in this repository yet, despite doctor already reporting on all nine adapters' availability.
  • docs/antivirus-exclusions.md documents that an AV/EDR quarantining or deleting nikto, sqlmap, ZAP or a Nuclei template mid-install is an expected interaction with this toolchain, not a broken install — worth checking before assuming doctor's report of a missing tool means the bootstrap script failed.
