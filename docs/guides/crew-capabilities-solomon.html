The Crew Plugin: What It Does and Why

The combined guide: high-level and technical in one document. Two companion documents split it: crew-overview for readers without technical depth and crew-technical-reference for the people who run it. Written against crew 0.20.11.

In one paragraph. Crew turns Claude Code from a single assistant into a small, disciplined software team. One agent manages, one investigates, one implements, an independent one from a different AI vendor reviews, and automatic gates stop anything that fails from being merged or released. Everything it knows about a codebase is written down in files that live with the code, so nothing depends on one person's memory or one chat session. It exists because an AI that writes code, reviews its own work, and never loses focus is a fiction; crew makes each of those a separate, checkable step.

1. The Problem It Solves

Left to itself, an AI coding assistant has four habits that cost real money:

  • It marks its own homework. The same model that wrote a change is the one saying it is fine.
  • It loses the picture. Each session starts from nothing. It does not know how the database is shaped, which service calls which, or what broke last month.
  • It wanders. Asked to fix one thing, it notices five others and fixes those too, and the ticket you asked for arrives with strangers attached.
  • Nothing stops it. A wrong command against a production database, or a merge with a failing test, goes through unless a human happens to be watching.

Crew answers each habit with a mechanism rather than an instruction: a separate reviewer, a written code map, a scope rule with an enforced write boundary, and gates that block.

2. How It Works, in Plain Terms

Think of it as a very small consultancy inside your editor. You write a ticket. A manager (the PM) decides who should do what and keeps the overall picture. A developer takes the ticket into a private workspace and does only that job. When it is done, a reviewer from a different company reads the change looking for defects, and reports them in a fixed format. A set of automatic checks runs before anything is merged or promoted, and if one fails, the release stops. Every decision and every lesson is written into files in the repository, so the next session, or the next person, starts where this one left off.

The technical version of the same sentence: file-backed tickets; one implementation session in its own context; an independent QA pass by Codex, Copilot or a fresh Claude context, whichever probes clean; deterministic gates wired into Claude Code's hook system; and a code map, code graph and diagrams kept in version control.

A role earns its place only if it buys an isolated context, a restricted tool set, or genuinely independent eyes. A persona in a prompt buys none of those, so crew does not ship "a business analyst agent" for its own sake. The command /crew:scale reads the review metrics and recommends growing, shrinking or staying.

5. Safety: The Gates and Guards

Claude Code lets a plugin register "hooks": scripts that run automatically at fixed moments, whether or not the model agrees. Crew uses them for the checks that must not depend on anyone remembering. A hook that can block a turn ships off and is switched on deliberately.

When it runsWhat crew does thereWhat that means
Session startBriefs the PM with project state and any handoff note; syncs the platform config.Every session begins knowing where the last one stopped.
Before a shell commandGuards: refuse terraform apply and tofu apply, force-push, admin merge; production database and host patterns once declared.A wrong command against production is refused, not regretted.
Before a file writeThe role write guard: each role may write only where its own definition allows. The PM's scope is notes, tickets and diagrams.The manager cannot quietly become the developer.
Before context compactionWrites the handoff note.Nothing is lost when the conversation is summarised.
On a notificationPulses the PM with what changed.Work landing elsewhere is noticed.
At the end of every turn (the Stop gate)Runs the verification map for the files that changed; blocks the turn on failure; now keeps the per-rule record even when one rule in the batch fails.The safety net under every change, and no longer all-or-nothing.

Two further gates sit outside hooks: the merge gate (Bitbucket or GitHub branch protection, driven by the same map) and the promotion gate, which refuses to promote without a row in the promotions log and, when configured, without a change request.

Every guard resolves to the narrower of the repository and machine-wide settings, so a cloned repository cannot loosen a machine's policy, and an unreadable setting resolves to the strict value, never to "off".

6. Knowledge: What Crew Remembers, and Where

  • The code map (.crew/codemap/): one prose file per subsystem, every claim marked as derived from a specific line of code or as judgement, each anchored to a commit so staleness is detectable, not guessed.
  • The code graph (graphify-out/): a mechanical graph of every symbol and call, rebuilt by a hook after each commit, queried by the explorer.
  • Diagrams (docs/diagrams/): Mermaid sources with anchors, refreshed only when the code they cite moved.
  • Runbooks, ADRs, changelog, handoff notes: the durable record, kept by the scribe and the docs commands.
  • Review metrics (.crew/metrics.md): one row per review, which is how /crew:scale and the PM's health signal know whether tickets are too large or a role is earning its place.

Everything above lives in the repository. Crew deliberately keeps nothing that only one machine or one chat can see.

7. What Changed Recently, and What It Means

Crew is at 0.20.11. The most recent fix, recorded in CHANGELOG.md's [Unreleased] section, closes three problems in the Stop gate and the PM in one pass.

ChangeWhat it means for you
The Stop gate kept no evidence when one rule failed.Before: a single failing check discarded the passing record of every other check that turn, so the next turn re-verified everything. Now: each rule's own outcome is recorded on its own, and only the rule that actually failed is left unrecorded.
A Git Bash python3 landmine reached the gate and three hooks.The gate now builds a python3 shim from a proved resolver only when python3 is genuinely absent, never shadowing python or py, and fails closed with a remediation hint when nothing resolves. context-watch, pm-brief and platform-sync go through the same strict resolver.
The PM read project state once per pass, not once per decision.It now re-reads crew_state.py's output plus HEAD, branch and working-tree status before every dispatch, and checks its own HEAD position again on every return, so a backward, sideways or foreign-forward HEAD is reported rather than missed.
render.sh handles flags in any position.It now exits 1 on an empty diagram directory and 2 on contradictory flags, renders to a temporary file so a failed re-render never overwrites the last good diagram, and prints separate ok/skipped/failed counts.

Earlier in the 0.19.x and 0.20.x line: the idle rule stopped agents stalling forever waiting for a notification that would never wake them; a behaviour-eval suite started testing the rules against a live model rather than only reading them, and its first run caught the PM writing code itself; the role write guard now mechanically enforces each role's write scope, off by default and the strictest layer wins when enabled; and every registered PowerShell hook now stands down off Windows, closing a defect where a host with both interpreters silently ran every hook twice.

9. Getting Started

  1. Install the marketplace and the crew plugin in Claude Code, then /reload-plugins in any open session.
  2. In a repository, run /crew:init. It is phased and resumable; nothing is written without saying so.
  3. Build the smoke harness when init asks. Everything downstream stands on it.
  4. Run /crew:onboard so the crew learns the codebase once and writes it down.
  5. Write a ticket with /crew:ticket, then /crew:work. Read the review. Merge when the gate is green.
