# T-0052 one split rulebook for /crew:split and /crew:autopilot split, every tracker: oversized ticket -> child tickets, cohesive-but-large -> plan PR slices          status: spec   risk: high
depends-on: T-0011, T-0012, T-0019, T-0037
## Intent
One split rulebook, `crew_split.py`, holds `/crew:split`'s judgement as code: split only on stated evidence, 2-5 children, every acceptance criterion placed verbatim or the split stops, each child's exclusions stated, and "not too big" reported as a result. `/crew:split` and `/crew:autopilot split` both call it. `/crew:split` drops "Jira only" and works in files and Obsidian mode with the same rules and the same confirmation. Its Jira path stays as it is, and SDP mode stops with a clear message in both.

Autopilot's `next` runs the size check once after spec and once after plan. When a measured trigger fires, autopilot writes a `split.md` decision through the rulebook, with one of three outcomes. **split**: approved under T-0012's split rule, where the owner's yes is always required in Jira mode; children are minted with T-0019's `mint` in files/Obsidian mode; the parent's text is kept as `spec.pre-split.md`; and the parent becomes T-0037's `superseded`. **slices**: the plan carries a `## PR slices` section, and each slice runs implement, review, done and T-0011's ship in order, as its own PR. **not-too-big**: said, recorded, and the run continues.
## Exclusions
- No mid-implement split and no re-slicing of a finished diff. The check runs after spec and after plan only, and slices are fixed in the approved plan before any code exists.
- Autopilot never creates a Jira issue. In Jira mode a split always stops for the owner, who runs `/crew:split <KEY>`, whatever `autopilot.approval` says.
- No SDP split, in `/crew:split` or in autopilot. SDP mode stops, naming the reason.
- No new ticket status. The parent becomes `superseded`, T-0037's word. No `split` or `cancelled` status is added here.
- No change to `/crew:split`'s Jira mechanics: MCP discovery, cloudId caching, sub-task-or-linked-issue choice, the parent comment and the cache files stay as they are. Only the judgement moves into shared code, and the "Jira only" precondition is removed.
- No change to `crew_ticket.mint`'s contract (T-0019), `split_policy`'s rule (T-0012) or `ship_decision` (T-0011). This ticket calls them.
- No approval grammar in the UserPromptSubmit hook. A `human` split approval is `/crew:split`'s existing in-chat confirmation, typed by the owner. A `split:<id>` hook receipt, like T-0012's `goal:<slug>`, is a follow-up that needs the owner's explicit yes, because it extends a blocking hook.
- No thresholds in config. They are constants in `crew_split.py`, each carrying its evidence in a comment, so a change to one is a reviewed code change.
- Autopilot does not re-open a parent's children as one run. Each child is its own ticket and is driven by its own `run`, or by T-0012's backlog.

- **PR slices: stacked or independent.** Decided, following the recommendation. Slices run one lifecycle at a time. Under `ship: merge`, slice k+1 branches from the default branch after slice k merges (independent). Under `ship: pr`, or while slice k is unmerged, slice k+1 branches off the default branch when its steps' Files share nothing with any unmerged earlier slice, and off that slice's branch otherwise (stacked, with the PR base set to it). Every slice merges with `merge_argv`'s merge commit (D-028).
- **Review budget per slice (the direction gave no recommendation).** Decided: each slice gets its own `BUDGET` rounds. A ticket's budget is 2 rounds (measured, not four), and sequential slices each need at least one review, so a shared budget would make a 3-slice ticket unreviewable. The mechanism is the successor pattern: `review_ledger.open_slice` appends a `slices` row and `_spent` counts from the latest successor or slice row. Rounds spent on earlier slices stay in the ledger.
- **The parent's status after a split.** T-0037's `superseded`, with `split-into: <ids>` on its own line under the spec header. T-0037 is therefore a dependency of this ticket, added here (it is not in the INDEX row). If T-0037 has not merged when this ticket is implemented, step 4 stops rather than inventing a status.
