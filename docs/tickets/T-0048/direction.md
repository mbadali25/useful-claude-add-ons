# T-0048 full crew 1.0 guide and a generated configuration reference          status: direction   risk: med   priority: high

## Problem
crew 1.0 has five task guides (`docs/guides/crew/src/README.md:9-16`) and no single document that explains the whole plugin: the four roles, the lifecycle and its approval receipt, review rounds and owner acceptance, refresh artifacts, the guards, autopilot, trackers, multi-session work, Windows and troubleshooting. Its configuration reference, `plugin/crew/CONFIG.md`, is hand-written and has drifted: it says 44 global-settable keys (`:214`), heads its global table "66" while listing 63 rows (`:636-639`), and heads its repo-only table "all 41" while listing 47 rows (`:740`). The code has 119 leaves, 66 of them global-settable, so 53 are repo-only (`plugin/crew/tests/test_crew_config.py:275`, and `leaf_paths` run on origin/main 1e0706ac). The allowed values of most keys are not declared anywhere a script can read. Nothing records the version a key arrived in. Keys from approved tickets that have not landed are documented nowhere.

## Decisions (owner, Matthew Badali, 2026-09-26)
- Request: "Also need to create a full documentation guide for the new crew and one separate [document] for all the crew configuration settings and possible values."
- **Where: repo docs + shared page (recommended option taken).** Both documents live in `docs/guides/crew/`, beside the existing guides: Markdown source under `docs/guides/crew/src/`, built exactly as the existing ones are built. Each is also published as a private shared web page once ready. The main session does that publish; this ticket's code does not.
- **How: generated from code (recommended option taken).** A script builds the settings reference from crew_config's own defaults and validators. It covers every key, its allowed values, its default, which layer may set it (repo `.crew/config.json`, global `~/.claude/crew/config.json`, or both, and whether it ratchets), and the version it arrived in. `scripts/check-marketplace.py` fails when the committed reference is stale.
- Settings from tickets that have not landed go in a separate "coming" section, each naming its ticket: `autopilot.approval` and `autopilot.questions` (T-0010); `autopilot.ship`, `autopilot.knownFailures` and `autopilot.ciTimeoutMinutes` (T-0011); `autopilot.maxLanes` and `autopilot.reviewPolicy` (T-0029); `autopilot.deploy` (T-0045); `guards.deployWorkflow` and `environments.workflows` (T-0009); `route.enabled` (T-0023); and others found in approved specs. When a ticket lands, its keys appear in the generated table, because they are then in the code.
- Priority: high.

## Recommendation
- Add one declarative table, `plugin/crew/hooks/scripts/crew_keys.py`. Each row is a key: its allowed values, a one-line summary, the version it arrived in, and, only where the code cannot say it, a layer rule. Where a value tuple already exists and a validator reads it (the ratchet tiers in `crew_guards.RATCHETED_KEYS`, `QA_PROVIDERS`, `DEV_PROVIDERS`, `AUTHORITIES`, `TICKET_GRANULARITIES`, `crew_ticket.MODES`, the auto-clear methods), the row points at that same object, so the validator and the generator read one definition. Where a validator is a code branch (`autopilot.mode`, `autopilot.maxPhases`, `resume.auto`, `context.autoClear.enabled`), a test runs every declared value, and one undeclared value, through the real reader. Where crew validates nothing, the reference says "not validated" and names the file that reads the key. It never implies a check that does not exist.
- The same module holds a `COMING` list with the same row shape plus a ticket id. A test fails when a COMING key is in the code. So a landing ticket must move its rows into the table, and it gets told which ones.
- The generator, `docs/guides/crew/src/config_reference.py`, writes `configuration-reference.md` and a generated block inside `plugin/crew/CONFIG.md`. Its `--check` mode is called by `scripts/check-marketplace.py`. The guide, `docs/guides/crew/src/guide.md`, is hand-written. Every section cites the command or file it describes, and a script checks those citations.

Recommendation: replace CONFIG.md's hand tables (sections 10 and 11) with a generated block between markers. The gate checks it, and CONFIG.md's prose sections, the "why", stay hand-written. That is a follow-up, not this ticket.

Keys already in the first template (e9bf1438, crew 0.11.0) read "0.11.0 or earlier". Recommendation: a key added later gets its version in the land commit, beside the version bump, and reads "unreleased" until then. The gate cannot tell a branch from main, so it does not fail on "unreleased".
- D5. The committed `crew-1.0-troubleshooting.html` is stale against its own source on origin/main. A rebuild adds the section "Auto-Clear Did Nothing on Windows" at line 448. Recommendation: rebuild it here (one command, no source edit), and have the new `build.py --check` cover all seven guides. Alternative: check only the two new guides and file the drift to TODO.md.
- D6. Recommendation: HTML, DOCX and PDF for both new documents, like the existing five guides (`build.py`'s default). The decision text says "built HTML". **Decided (owner, 2026-09-26): "You can build all three."**
- D7. Recommendation: one self-contained guide that links to the five task guides for depth, not one that replaces them.
