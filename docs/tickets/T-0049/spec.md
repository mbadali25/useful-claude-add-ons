## Intent
`crew_inflight.py` records who is driving a ticket right now: one marker per ticket under `<git-common-dir>/crew/inflight/`, shared by every worktree of one clone, refreshed by a heartbeat. `holds(root, ticket, ...)` reads it and answers `free`, `mine`, `live`, `stale`, `elsewhere` or `unknown`, writing nothing. `/crew:autopilot` claims the ticket before its loop, and `crew_autopilot.py next --runner autopilot` stops instead of double-driving a ticket another runner holds, or one whose holder died or stalled. A stale marker is never removed automatically: the stop prints the owner's `clear` command.
## Exclusions
- No notification. The `Lane stalled` / `Lane state unknown` pings are T-0060's, which reads `holds()` and writes nothing here (`origin/T-0060-build:docs/tickets/T-0060/spec.md:13`).
- No stall timer, daemon or watcher. Staleness is computed when a marker is read. The heartbeat child beats one marker and exits with its holder.
- No new hook registration. No change to the Stop gates, the scope guard or the review harness (`HARNESS` in `scripts/check-tooling-pr.py:58-84`).
- No cross-clone or cross-machine coordination (T-0030's `crew_coord.py`, unmerged). Two clones of one repository do not share `<git-common-dir>`; that case is out of scope and documented.
- No automatic clear, and no clear by age. `crew_train.py:63-67`'s rule: breaking a hold by age is how two writers both win.
- No wiring of workflow lanes outside this repo. The CLI (`claim --runner lane`) is the interface; the owner's workflow scripts adopt it. OWNER CHECK.

## Unknowns
- **Does a detached heartbeat child survive the Bash tool call?** Claude Code may run each Bash call in a sandbox that kills its process group (Linux bubblewrap, macOS seatbelt) or not (Windows). Plan step 1 measures it on Linux and, where available, Windows. If the child dies with the call, the build stops and asks. OWNER CHECK: the fallback recommended is a beat on every `next --runner autopilot` call that reads `mine` plus a beat from the existing crew-context `PostToolUse` hook for a session holding a marker (no new registration); both make the TTL a bound on time between tool calls, not wall time.
- **Holder identity.** The marker records `session` (`CLAUDE_CODE_SESSION_ID` if the Bash environment carries it), `pid` (the long-lived Claude Code process: the nearest ancestor of the claiming process whose executable is `claude` or `node`), `pid_start` (start time, to catch pid reuse), `pidns` (Linux `/proc/self/ns/pid` inode) and `boot_id`, `host`, `worktree`. `mine` needs the same worktree AND the same session AND, where measured, the same pid (T-0030 FIX: session alone lets `--resume` take a working claim). Step 1 measures which of these the Bash environment exposes. OWNER CHECK.
- **The sandbox pid probe.** Inside a pid namespace `os.kill(pid, 0)` raises ESRCH for a live process (T-0030 BLOCK). Decided: the pid is probed only when `host`, `boot_id` and `pidns` all match the reader's; otherwise the probe is `unmeasured` and the heartbeat decides alone. A probe that errors is `unmeasured`, never `gone`.
- **What `elsewhere` means.** Reconstructed: a holder whose heartbeat is fresh and whose `worktree` is not this one. `live` is a fresh holder in this worktree that is not `mine`. Autopilot stops on both, `elsewhere` as `handover-elsewhere` ("drive it from <worktree>"), so T-0060's "elsewhere sends nothing" holds because the work is progressing in another checkout. OWNER CHECK.
- **Clock skew.** A `heartbeat_at` more than 120 s in the reader's future is `unknown` ("heartbeat in the future"), never `live`.
- **The line budget.** autopilot.md has one line free and T-0060 needs one after this ticket. This ticket's edits must fit by rewording in place (net 0 lines is the target). If they do not, stop and ask; never raise `AUTOPILOT_MAX_LINES`. OWNER CHECK.
- **The tooling-PR rule.** `sabotage_inflight.py` is harness today. If change 6 of the QA analysis (a feature's own `sabotage_<area>.py` is a test) has landed when this is built, the table rides in the feature PR; otherwise plan step 7's split applies. OWNER CHECK.

## Contract (what T-0060 and later tickets may rely on)
- Module `plugin/crew/hooks/scripts/crew_inflight.py`. Constants `TTL_SECONDS = 1800`, `HEARTBEAT_SECONDS = min(600, TTL_SECONDS // 3)`, `STATES = ("free", "mine", "live", "stale", "elsewhere", "unknown")`, `RUNNERS = ("autopilot", "lane", "session")` (OWNER CHECK: the runner names).
- Marker `<git-common-dir>/crew/inflight/<ticket>.json`, one per ticket: `{"schema": 1, "ticket", "runner", "token", "session", "pid", "pid_start", "pidns", "boot_id", "host", "worktree", "branch", "since", "heartbeat_at"}`, timestamps ISO 8601 UTC. Created with `os.link` from a complete temp file (fails if one exists); rewritten under `<ticket>.json.lock` (crew_train's `_Lock` shape) by `os.replace`. `events.jsonl` beside it logs `claim`, `release`, `clear`.
- `holds(root, ticket, runner=None, session=None) -> dict`: `{"state", "ticket", "runner", "since", "heartbeat_at", "worktree", "why", "clear"}`. `state` is always one of `STATES`; every read, parse, shape, probe or git failure returns `unknown` with `why`; it raises only for an invalid ticket id (`crew_ticket.check_ticket`). `clear` is the exact owner command, set when `state` is `stale` or `unknown`, else `""`. Writes nothing, creates no directory, writes no bytecode.
- CLI: `claim --root . --ticket <id> --runner <r>` (prints `claimed`, `refreshed` for `mine`, or `refused: <state> ...`, exit 0/2/3), `release --root . --ticket <id>` (only the holder; else refused), `holds --root . --ticket <id> [--runner <r>] [--json]` (one `state=... runner=... since=... worktree=... why=... clear=...` line, exit 0 even for `unknown`), `clear --root . --ticket <id> --by <who> --reason <text>` (owner only; refuses unless the state is `stale` or `unknown`, logs the event), `beat-loop` (internal, started by `claim`).
- The `clear` command text is `python3 "${CLAUDE_PLUGIN_ROOT}/hooks/scripts/crew_inflight.py" clear --root . --ticket <id> --by <you> --reason "<why>"`.
- autopilot: `next --runner autopilot` adds phase `in-flight` (stop) and phase `handover-elsewhere` (stop). Their reasons name runner, ticket, since, worktree, and for `stale`/`unknown` the clear command. `FIXED_STOPS` gains `in-flight` and `handover-elsewhere`; `AUTONOMOUS_STOPS` gains `clear-inflight`.

## Risk
High. This is a guard on autopilot: an unknown read as `free`, or a dead lane read as `live`, either double-drives a ticket or hides a stall from the owner and from T-0060's ping. It also starts a detached process. Mitigations: six fixed states with `unknown` as the default arm; read path separate from write path; never clear by age; sabotage per branch; the heartbeat measured in the real tool environment before any code.
