# T-0044 unattended runs hold read-only cloud credentials          status: spec   risk: high
## Intent
A new launcher, `crew_unattended.py launch -- claude ...`, starts an unattended Claude session holding short-lived AWS credentials for an owner-named read-only identity, or for a nonProd write identity the owner named for one `environments.nonProd` environment. The machine's credential stores are denied to that session's Bash and file tools through Claude Code's sandbox and permission deny rules. Before it starts anything, the launcher must prove four things: the identity comes from the machine layer only, the exported credentials are temporary, `aws sts get-caller-identity` returns the named identity, and a real sandboxed Bash call inside the sealed settings cannot open the stores. If it cannot tell any one of them, it refuses. It never falls back to ambient credentials, and it never stores, copies or logs a credential. This is the boundary T-0005's command-line guard cannot be: it holds whatever the command line says.
## Exclusions
- Azure, TFC/HCP and every provider other than AWS: config keeps a provider seam (`unattendedCloud.<provider>`), and any provider key other than `aws` refuses as not implemented. No `az`, no TFC token exists on this machine.
- Option D (a separate OS user or container for unattended runs) is not built. It is the named upgrade path when the sandbox layer has gaps (Unknowns).
- No change to `cloud_guard.py` decisions. T-0005's guard, its environment table, and T-0047's direct-use gaps stay as they are. A guard-side check that an unattended session was started sealed is a follow-up, not this ticket, because a repo's `.claude/settings.json` `env` block could forge any marker variable.
- Crew does not start unattended sessions on its own. `/crew:autopilot`, auto-resume and auto-clear keep running in the session that already exists, and a hook cannot change that session's environment. The launcher is the one entry point, and the owner (or the owner's scheduler) runs it.
- Native Windows: the launcher refuses with a named reason (`sandbox probe not implemented for native Windows`). It never degrades to an unsealed launch. No `.ps1` twin.
- Crew never writes to `~/.aws`, never runs `aws sso login`, never refreshes or caches a token, and never writes a credential to disk. The sealed directory holds a region-only AWS config and the sealed settings file, nothing else.
- No change to `~/.aws/credentials` permissions or contents. The host holding long-lived keys is reported to the owner, not fixed here.
## Evidence
- No crew entry point starts a process with its own environment today: `/crew:autopilot`'s reader is read-only and runs in-session (`plugin/crew/hooks/scripts/crew_autopilot.py:1-12`); auto-resume starts no turn (`plugin/crew/hooks/scripts/crew_resume.py:14-18`); auto-clear types into the existing window (`plugin/crew/hooks/scripts/crew_autocycle.py:1-50`). So the environment of an unattended session is set only where it is launched, which is where this ticket puts it.
- "Unattended" is detected at `plugin/crew/hooks/scripts/cloud_guard.py:2955-2972` (`CREW_UNATTENDED`, `CI`, `bypassPermissions`/`dontAsk`). The launcher sets `CREW_UNATTENDED=1` so the T-0005 guard judges the session as unattended.

The repo-only `cloud` pins are at `plugin/crew/hooks/scripts/crew_guards.py:239` and `plugin/crew/hooks/scripts/cloud_guard.py:2496`. `environments_config` (repo layer, T-0005) is at `plugin/crew/hooks/scripts/cloud_guard.py:2526`.

- Host, measured 2026-09-27 (aws-cli 2.36.50):
  - `~/.aws/credentials` is mode 644 and holds static keys under 10 profile sections, including prod-named ones.
  - `~/.aws/cli/cache` holds a cached credential JSON.
  - `~/.aws/config` has `sso-session anew-sso` and profile `<admin-profile>` (`sso_role_name = AdministratorAccess`). Profile `anew` names no role.
  - There is no `~/.azure`, and `~/.terraform.d` has no `credentials.tfrc.json`.
  - The session environment has no `AWS_*` variables.
  - `aws configure export-credentials --format process` prints a JSON object. Only temporary credentials carry `SessionToken` and `Expiration`.
- Claude Code 2.1.283, from its settings schema: `sandbox.filesystem.denyRead` is "Merged with paths from Read(...) deny permission rules". `sandbox.failIfUnavailable` exits at startup only when the backend cannot start.
- Sandbox, measured 2026-09-27 with `claude -p --settings` (`sandbox.enabled`, `failIfUnavailable`, `allowUnsandboxedCommands: false`, `filesystem.denyRead` plus a `Read(...)` deny, fixture under `/root/crew-tmp/t-0044/sbx`):
  - Every Bash call failed before running, including `echo` and with `enableWeakerNestedSandbox: true`, with this error: `apply-seccomp: write /proc/self/setgroups (nested userns is capability-restricted; caller must provide CAP_SYS_ADMIN): Permission denied`.
  - `kernel.apparmor_restrict_unprivileged_userns = 1`. Plain `bwrap --unshare-user` works.
  - The Read tool on the denied path returned `File is in a directory that is denied by your permission settings.`
  - Grep and Glob are absent in this build (`No such tool available: Grep`).
  - So on this host the sandbox starts, `failIfUnavailable` does not fire, and nothing runs. Only a real probe can tell "sealed" from "unusable".
## Unknowns
- Is there a read-only permission set in the owner's SSO assignment? Unresolved and not guessed. Until the owner names `unattendedCloud.aws.readOnly.identity` in `~/.claude/crew/config.json`, every launch refuses with `no read-only identity named`. That refusal is the designed behaviour, accepted.
- The sandbox is unusable on this host (Evidence). Every launch here therefore refuses with `sandbox: unavailable` and the verbatim seccomp error. Making it usable is the owner's call on the host: allow Claude Code's sandbox under the AppArmor userns restriction, or take Option D as a follow-up. It does not block implementing A, because the suites drive fake `aws` and `claude` shims and never need a working sandbox.
- Does the sandbox deny cover interpreters, scripts and copied binaries? It could not be measured on this host because the sandbox runs nothing. Resolved per launch instead of by one measurement: the probe opens every store with `head -c1` and with `python3 -c open(...)` inside the sealed session, and any store it can open refuses the launch. That makes the probe the check.
- Grep/Glob tools: absent in 2.1.283. The sealed settings deny `Read(<store>/**)`, and Claude Code applies that to its file-reading tools. If a later build adds Grep/Glob tools that ignore Read denies, that is accepted as risk until measured. It is recorded in the README.
- Pre-run network calls: `aws sts get-caller-identity` (read-only, free) and one headless `claude -p` probe call per launch. Both are accepted: the direction recommends the STS call, and the probe is the only measurement that tells sealed from unusable. The probe's verdict is parsed from the `stream-json` tool result, never from the model's prose. A probe that makes no tool call is `unknown` and refuses.
- A repo's `.claude/settings.json` `env` could re-point `AWS_CONFIG_FILE` or `AWS_SHARED_CREDENTIALS_FILE` at the machine stores inside the sealed session. Analysed and accepted: the stores themselves are denied to Bash and the file tools, so re-pointing reads nothing. The probe runs with the repo's settings loaded, so it measures that case too.
- Credentials expire mid-run: the run loses AWS access and fails closed. Accepted. The launcher refuses when less than 15 minutes of lifetime remain.
- `/proc/<pid>/environ` of processes outside the sealed session: the launcher replaces its own process with `claude` and passes only the sealed environment, so its chain carries only the temporary credentials. Other root processes are accepted as risk and named in the README.
