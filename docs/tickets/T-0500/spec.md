# T-0500 crew init after migrate re-offers phases whose definition changed since marked done, and a phase whose note records a breakage cannot stay done unverified (aws-ops report item 13)          status: spec   risk: med
## Intent
`.crew/STATUS.md` records which crew version each phase row was marked against (a `crew: <version>` header line, written with every rewrite), every `## Phase N` section of `plugin/crew/skills/crew-setup/phases.md` carries a machine-readable `<!-- phase-rev: <version> -->` marker naming the crew version at which its definition last changed materially, and a new read-only script `plugin/crew/hooks/scripts/crew_setup_status.py` compares the two and prints one line per `done` row that is (a) marked against a version older than its phase's marker ("definition changed since marked"), (b) unknown because the file has no `crew:` line ("could not tell when marked"), or (c) carrying a note that matches a short documented breakage list ("note may record a breakage"), then a `re-verify:` summary and the `crew:` line to write next. `/crew:init` (no argument and `--status`) runs it before choosing where to resume and offers each flagged phase for re-verification before the first non-`done` one; `/crew:migrate` preview and apply print its lines so a 0.20 table is flagged the moment it enters 1.0. The checker never rewrites a row and migrate never stamps the file: the stamp is written only when a phase is actually run or re-verified. This is direction.md's Option 1 with open questions 1-4 settled as written there, one crew patch past origin/main at push time (1.0.70 against `a61a6f38`, crew 1.0.69; re-bumped if main moved).

## Unknowns
- **Marker placement and syntax.** Decided: the line immediately after each `## Phase N — <title>` heading (a blank line between is allowed; the parser looks at the next three lines) is `<!-- phase-rev: X.Y.Z -->`. HTML comments do not render in the skill text the model reads as prose, and `validate-prompts.py` only parses frontmatter. A heading with no marker within three lines is could-not-tell for the whole run (exit 3, naming the phase), never silently unchecked. Accepted.
- **Version comparison.** Decided: dotted integers compared as tuples (`(1, 0, 9) < (1, 0, 10)`); a `crew:` value or marker that does not match `^\d+(\.\d+)*$` is could-not-tell for the rows it affects. A sabotage entry replaces the tuple compare with string compare and the `1.0.9 < 1.0.10` test must go red. Accepted.
- **Breakage word list.** Decided, documented in the script's docstring and `phases.md`: `broken`, `failing`, `not working`, `provider none`, `unreachable`, `never arrived`, `timed out`, `no longer`, matched case-insensitively as substrings of the Notes cell of `done` rows only. Misses are accepted (the prose rule is the authority); false positives cost one re-verification. Accepted as risk.
- **Where the current version comes from when the plugin is installed from a cache.** `${CLAUDE_PLUGIN_ROOT}/hooks/scripts/crew_setup_status.py` resolves `../../.claude-plugin/plugin.json` from its own path, which exists in a cached install (the manifest is part of the plugin) and in this repo. If it is unreadable the script prints `current crew: could not tell (plugin.json unreadable at <path>)` and still runs the row checks; a test covers it by monkeypatching the path. Accepted.
