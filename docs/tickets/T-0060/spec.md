## Intent
T-0051's `crew_notify.py` gains the `blocker` event: a loud ping, led by a subject naming what happened, whenever work stops and only the owner can move it. Four reasons send it. **Approval waiting**: `/crew:autopilot` stopped at `approve` (a receipt that an edit made stale included), one message per run naming the ticket and `/crew:approve <id>`. **Review out of rounds**: the review ledger records the round that spends the last of the budget, and it carries a BLOCK. **Lane died or stalled**: autopilot's in-flight check (T-0049) reads another runner's marker as `stale`, which covers a dead pid and a heartbeat older than T-0049's TTL. **Stop gate refused**: the verify gate or the completion audit refuses the same ticket at Stop a second time in a row, after the session's own retry.

Each reason has its own subject (`Approval waiting`, `Review out of rounds`, `Lane stalled`, `Stop gate refused`), so the message says what happened before the repo and branch. The decision of which autopilot stop pings lives in `crew_notify.py run-stop`, tested code, not in `autopilot.md` prose.
## Exclusions

- No new hook registration. The Stop gates' exit codes are unchanged: a notify call placed before a refusal can neither change the verdict nor time the gate out. This ticket blocks nothing new.
- No stall timer and no daemon. The lane reason fires only when autopilot's in-flight check reads a marker, and the TTL is T-0049's constant. No stall timeout is invented here.
- No change to `crew_inflight.py` or `crew_autopilot.py` (T-0049 owns them). `run-stop` reads `crew_inflight.holds()` and writes nothing there.
- No wave-level or goal-level approval batch. A batch covers one `/crew:autopilot` run (T-0004's one ticket). T-0029 and T-0024 reuse `blocker` with kind `approval` and several ids once they land.
- No ping for infrastructure refusals of the Stop gates (no python, no temp file, lock failures). Those paths have no working python to send with. Only the verification-failed refusal of `verify-gate` and the verdict refusal of `completion_audit.py` are counted.
- No ping for the other autopilot stops (`done`, `maxPhases`, no-progress, a `live` in-flight holder, `handover-elsewhere`). A live runner is work in progress, not a blocker.
- No findings text, diffs, ticket bodies, file contents or secrets in any message (T-0051's payload rule).
- No change to `event_claim.py`'s election rules.

## Unknowns
- **Depends on two unmerged tickets.** Every T-0051 and T-0049 anchor above is re-read on main before step 1. Steps 1-3 and 5-7 need T-0051 only. Step 4 needs T-0049 on main; if it has not landed when the rest is ready, stop before step 4 and ask whether to ship without the lane reason (a spec amendment that moves acceptance 4 to a follow-up), never a stub that reads every marker as quiet.
- **The stall timeout.** Decided: T-0049's TTL (30 minutes in its spec), read through `holds()`. Accepted limit: a lane that dies while no autopilot run checks it is not pinged until the next check. A workflow lane that errors and leaves its marker behind is the same case, since its pid is gone and `holds()` reads `stale`.
- **An `unknown` holder state pings.** Recommendation, taken under the direction's approval: `holds()` answering `unknown`, or `crew_inflight` failing to import or raising, sends `blocker` kind `lane-unknown` (subject `Lane state unknown`, unblock `/crew:status`). Autopilot has stopped and cannot tell why, so staying quiet would be the unknown collapsing into the safe-looking value (CLAUDE.md, Lessons). Deduped like any other reason.
- **Is `prompt_id` present on a Stop payload?** It is documented in the `Notification` example only. The Stop-refusal identity uses `prompt_id` when present, else a digest of the normalised payload, so the two Windows flavours count one refusal once. If two consecutive Stops were byte-identical with no `prompt_id`, they would count as one, and the ping would come one refusal late. Accepted as risk, and step 5 tests both shapes.
- **`autopilot.md` is at its line budget.** The pre-split plan added one line per case. Here it is one `run-stop` line at the report, which decides every case in code. If T-0049 has filled the budget by then and the line does not fit by rewording the report section, stop and ask rather than raise the budget.
- **A `blocker` with no known kind** (a legacy `notify.sh review ...` call, mapped by T-0051) is sent with the subject `Blocked`, never dropped.
- **Codex is out until 2026-10-01**, so the review may be same-family. Accepted as risk and announced.
