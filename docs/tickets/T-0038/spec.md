# T-0038 fold /crew:upgrade into /crew:migrate: migrate upgrades a pre-0.20 config itself, and upgrade.md becomes a removal stub          status: spec   risk: high
## Intent
`/crew:migrate` accepts a pre-0.20 `.crew/config.json` (no `schema` key, or an integer `schema` from 1 to 6) and brings it up to the current schema itself, using `crew_upgrade.upgrade_config`, the same code `/crew:upgrade` ran. It then continues its normal migration in the same run. The preview shows both stages, one apply backs up and writes both, and one `--rollback` restores `.crew/config.json` byte-identical and removes the rest. `plugin/crew/commands/upgrade.md` shrinks from a 375-line procedure to a removal stub, like `work.md` and `ticket.md`. `crew_upgrade.py` stays as a library that `/crew:onboard --refresh` and the tests still use. Every document that names `/crew:upgrade` as a live command is updated in the same change.
## Exclusions
- A config at schema 7 (every 0.20 config, because schema 7 shipped in crew 0.19.31) and a repo that already has `crew.json` behave exactly as today. Every existing `test_migrate.py` test passes unchanged.
- A `schema` that is present but not a usable integer (`null`, `"7"`, `true`, a float, 0 or below) is still refused, and nothing is written. Schema 8 or above is still refused. The existing `test_unknown_schema_is_refused_and_nothing_written` cases stay as they are.
- Migrate does not do the codemap half of the old `/crew:upgrade`: no graph build, no `--derived` reconcile, no `.crew/codemap/UPGRADE.md`, no `.crew/codemap.v1.bak/` and no `.crew/config.json.v1.bak`. The codemap stays untouched, as migrate's table already says. `/crew:onboard --refresh <subsystem>` is the path for graph facts, and its own procedure is unchanged apart from the wording that names `/crew:upgrade`.
- No change to `crew_upgrade.upgrade_config`, `run()`, `CONFIG_BLOCKS`, the schema number or any migration rule. `crew_upgrade.main`'s code stays the same, because `test_guards.py:234` reads its source and sabotage anchors target its text. The only edits there are two user-facing strings that tell the user to re-run `/crew:upgrade`.
- The command is not deleted. It stays as a stub, so the command count (35) and the install scripts' "35 commands" text do not change. Removing the stub is a later ticket.
- The old upgrade.md step 5b model-pin table is not carried over. It offers pins for roles 1.0 deleted (`TODO.md:4110`). `/crew:model` and `/crew:config` own model pins.
- `/crew:upgrade` is not added to `scripts/check_instructions.py`'s `STALE_NAMES`. The historical `/crew:upgrade` mentions in CHANGELOG entries, `docs/superpowers/`, `docs/review/`, `docs/adr/`, the old release notes in `README.md`, `plugin/README.md` and `plugin/UPDATE.md`, and code comments that explain past behaviour all stay. The only `TODO.md` edits mark entries that cite `commands/upgrade.md` line numbers as moot.
- Nothing is written to `~/.claude/crew/config.json`. `crew_autoclear_setup.py` and `crew_instructions.py` do not change.

## Unknowns
- Stub or clean delete. Decided: a stub. It follows direction.md's recommendation and the `/crew:work` precedent. It keeps the 35-command claims and the install scripts' text unchanged. A clean delete would need both install scripts, three claims and the marketplace text changed. Flagged for the owner at approval.
- Which configs get the upgrade stage. Decided: no `schema` key, or an integer from 1 to 6. Direction.md said "no integer `schema`". That wording came from upgrade.md:7, but a schema 1 to 6 config is also pre-0.20. Today migrate maps it without upgrading `config.json`. With `/crew:upgrade` gone, that would strand it below `SCHEMA_CURRENT`. Flagged for the owner at approval.
- Unmigrated blocks. If `upgrade_config` leaves `notes["unmigrated"]` non-empty, the preview reports a CONFLICT naming each block, and apply writes nothing. A half-upgraded config never reaches crew.json. Pinned by a must-block test.
- `crew_upgrade` cannot load (moved or missing). Migrate stops with a named error and exit 1, and writes nothing. It never falls back to migrating the old config unupgraded. Pinned by a must-block test, and by a subprocess test that runs `crew_migrate.py` with no test `sys.path` help.
- Windows bytes. Migrate writes `config.json` as UTF-8 LF bytes from the same `json.dumps(..., indent=2, sort_keys=True)` call as `run()`. `run()` writes in text mode, so on Windows it produces CRLF. An agreement test compares the two on Linux only. Windows is not verified here, and the report says so.
- `crew_autoclear_setup.py apply-migrate` rewrites `context.autoClear` in `config.json` after apply (`migrate.md:77-81`). If it converts anything on a pre-0.20 repo, rollback then finds `config.json` edited and refuses it by name. That is the same thing it already does for `crew.json`. migrate.md says so. Accepted as risk.
- The quickstart guide rebuild needs `soffice` (`docs/guides/crew/src/build.py:240`). If it is not on the implement host, implement stops as needs-owner rather than committing an HTML-only rebuild.
- Collisions: T-0018 and T-0025 list commands. Whichever lands second updates its list. No other open ticket's Touch names `crew_migrate.py` or `test_migrate.py` (checked against `.work/tickets/*/spec.md` at implement).
- Version: one patch above origin/main's crew version at land time, read then with `git show origin/main:plugin/crew/.claude-plugin/plugin.json`.
