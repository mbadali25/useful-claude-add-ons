# T-0061 ticket base branch: scope base, review bundle and completion audit follow the repo's integration branch, not origin/HEAD          status: spec   risk: high
## Intent
A repository whose ticket branches are cut from an integration branch (`development` in TSS) gets a scope base measured against that branch. The base is not the merge-base with `origin/HEAD`/`main`, so the review bundle, the completion audit, the refresh check, `scope_report` and the webtest guard see the ticket's change and not the whole integration branch. A repo-only key `tickets.baseBranch` (default `null`, meaning origin/HEAD's target, as today) names the branch. `crew_ticket.py activate` records the scope base at branch cut, as `/crew:implement` step 1 already does. When the configured branch names no commit, the answer is "could not tell", with no base, never a silent fall back to `origin/HEAD`/`origin/main`/`main`.
## Exclusions
- No change to the verify gate's own base (`plugin/crew/hooks/scripts/verify-gate.sh:208-213`, `plugin/crew/hooks/scripts/verify-gate.ps1:484-486`). Its fallback is a superset, the safe direction, and it answers "what has not been verified" rather than "what did this ticket change". T-0068 owns both gate files right now. The follow-up is filed to `TODO.md` (open question 1).
- No change to `review.md` step 1a's no-python3 fallback (`plugin/crew/commands/review.md:126-137`). It runs only when `scope_base.py` could not run at all, so no config can be read. It keeps its "(fallback - scope_base.py did not run)" label.
- No change to `completion_audit.py`, `crew_refresh_check.py`, `scope_report.py`, `webtest_guard.py` or `review_patch.py` source. Each already treats a `None` base as unmeasured or failed (Evidence). They get the new behaviour through `scope_base`. `crew_refresh_check._fallback_hides` calls `scope_base._default_ref`, which keeps its name and signature.
- An exact entry (`"from": "HEAD"`) is never rewritten, whatever the config says. Only a fallback entry recorded against a different ref than the current base branch is re-derived (open question 2).
- A record that is gone or no longer an ancestor of HEAD still falls back to MORE (the merge-base with the base branch), labelled "(fallback)". Its reason now starts "could not tell where <ticket> started". This does not fail closed, because records are never overwritten and a rebase would then block `/crew:done` for good (open question 3).
- No config schema bump and no `crew_upgrade` migration. An absent `tickets` block reads as `null`, the same as today's behaviour.
- The key is not global-settable. It is absent from `default_global_config()`, like `scope.*` and `autopilot.*`.

## Unknowns
- Worktrees of a repo whose `.crew/config.json` is untracked (this repo) see no key and keep today's `origin/HEAD` default. Accepted as risk. CONFIG.md says the key is read from the checkout's own file, like `scope.mode`.
- T-0068 (in flight) edits `review.md`, `README.md`, `CONFIG.md`, `.crew/verify.json`, `sabotage.py`'s neighbours and the codemap. Whichever lands second takes a textual merge. Implement re-reads each file at origin/main before editing it. A behavioural conflict is a STOP.
- The TSS record for TSS-510 is `from: merge-base with origin/development` against the current key value `development`. Candidates are tried as `origin/<name>` first, so that entry's ref equals the current one and it is kept rather than re-derived. `test_a_fallback_recorded_against_the_same_ref_is_kept` covers this.
- Remote name: candidates are `origin/<name>` then `<name>`. A repo whose remote is not `origin` names the local branch or `<remote>/<name>` in the key, and any value containing `/` is tried as given first. Accepted as risk.
- Reviewer independence: Codex may be at its usage limit, so the review may be same-family. Accepted as risk, and announced when the review runs.
