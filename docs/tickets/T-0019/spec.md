## Intent
Two parts, built in this order.

(1) `crew_ticket.mint(root, title, status="ready", direction=None)`: the one way code creates a ticket. It takes the next free `T-####` (one past the highest `T-` number over `.work/tickets/` folders and `.work/INDEX.md` rows), claims it with an exclusive `os.mkdir`, writes the ticket's direction.md complete or not at all (temp file + `os.replace`), and only then asks T-0021's `crew_tracker.create` for the INDEX row (and, under `obsidian`, the vault note and Kanban card), followed by `crew_tracker.move` to `ready` when `status` is `ready`. A tracker answer of `id taken` releases the folder and tries the next id; any other tracker failure, or a direction write that raises, unwinds the folder and the direction so no ticket is left behind. Two concurrent mints never get the same id. Under a `jira` or `sdp` tracker (where `create` is delegated to MCP), a tracker that is `not configured`, or one that `could not tell`, `mint` refuses before claiming anything: a row it cannot write is a ticket autopilot cannot drive.

(2) `/crew:autopilot assign "<work>"` researches the work once, using crew:explorer for the repo and crew:researcher for outside facts. It writes a complete direction to a staging file under `.work/autopilot/`: a `title:` and a `risk:` line, then `## Ask` holding the owner's text verbatim, and `## Options`, `## Recommendation` and `## Open questions` in `/crew:brainstorm`'s format. `crew_ticket.py assign --root . --direction-file <f>` checks the staging file first (and that autopilot is armed). Only then does it call `mint` with the direction body, so the ticket's folder, its direction.md (with an `origin: /crew:autopilot assign` provenance line and the `title:`/`risk:` lines) and its tracker row (`ready`) appear together or not at all. Autopilot then runs T-0004's loop on the new ticket (sections 2 to 5 of `autopilot.md`): `resume --ticket <id>` activates it, open questions go through T-0010's `question_policy`, then spec, then plan, then the approve phase.

The approve phase is T-0010's, unchanged: `crew_autopilot.py approve --root . --ticket <id>` applies `autopilot.approval`. `self` approves; `risk` approves only a known `risk: low` spec header; `human` refuses. It also refuses without `scope.allowCliApproval: true`, when autopilot is not armed, and when the review ledger is UNKNOWN (unreadable). A NEEDS_REPLAN ledger does not refuse (T-0010 round 1: approving a distinct successor plan is the only way out of it; `approve` exits 3 when the ledger still refuses the plan). `next` names the approve phase only after spec.md and plan.md pass `crew_ticket.validate` and no open question is left unanswered. On exit 0, autopilot reports the `self-approved <id> under approval=<policy>, risk=<risk>` line by name and keeps running. On any other exit, or `human`, it stops and names `/crew:approve <id>` (section 3's rule, unchanged). Review acceptance and production deploys always stop for the owner (T-0010, T-0011, T-0005).
