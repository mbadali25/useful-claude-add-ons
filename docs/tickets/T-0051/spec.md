## Intent
crew's notifier becomes one Python module, `crew_notify.py`, that sends two kinds of message: `deploy` (every `/crew:promote` result, a pass silent and a failure loud) and `question` (Claude Code stopped and is waiting on the owner: a permission prompt, an AskUserQuestion, or an MCP elicitation, from the `Notification` hook filtered on `notification_type`). Each message leads with a subject from one `SUBJECTS` table - `Question`, `Needs permission`, `Promotion passed` or `Deploy FAILED` - then `[<repo>/<branch>]`, the active ticket and its phase, and what Claude is waiting on: the payload's own `message` plus the first line of the pending question or of the last assistant text, read from `transcript_path`, capped and redacted. A detached HEAD shows the ticket, never `HEAD`. An idle `idle_prompt` never pings, one waiting episode pings once until the owner has replied in that session, and the per-phase, per-review and per-ticket pings are retired. `blocker` is a reserved event name here, accepted in config and sending nothing, until T-0060 gives it a sender.

The Telegram send path is ported from the notify skill (429 `retry_after`, about 1/s pacing, HTML escaping). A fingerprint dedupe with a re-alert window (default 6h) lives under `<git-common-dir>/crew/notify/` and advances only on a confirmed send. The config is read from the machine-global `notify` block with the repo layer overriding it, and the notify skill's `telegram` block fills a missing token env or chat id read-only. `notify.sh` and `notify.ps1` become thin wrappers that keep `event_claim.py`'s one-sender election.

- **The AskUserQuestion `notification_type` is expected, not measured.** The 2.1.285 binary routes AskUserQuestion through the permission dialog (Evidence), so it should arrive as `permission_prompt` with `message` `Claude needs your permission to use AskUserQuestion`, about 6 s after the dialog opens. Nothing in the docs ties it to a type, and no live payload has been captured. Resolved before step 2 by step 1's live capture: a throwaway `Notification` hook that appends each payload to a scratch file, in an interactive session that triggers an AskUserQuestion, a Bash permission prompt, an idle wait of more than 60 s, and an MCP elicitation if a server offering one is available. The spec's type set and the `Question` / `Needs permission` split are then confirmed or amended. Until then `question` is: `permission_prompt`, `worker_permission_prompt`, `elicitation_dialog`, `elicitation_url_dialog` and `agent_needs_input`, and `Question` is chosen when the type is an elicitation or `agent_needs_input`, or when a `permission_prompt`'s `message` names `AskUserQuestion`; `Needs permission` otherwise. The list is overridable as `notify.questionTypes`, so a wrong guess costs a config line, not a release.
- **Measured vs documented.** `permission_prompt`, `idle_prompt`, `elicitation_dialog`, `elicitation_url_dialog` and `agent_needs_input` are documented and also read from the 2.1.285 binary. `worker_permission_prompt` is binary-only. None has been captured from a live hook payload yet. Step 1's capture records which ones it saw, and the rest stay labelled "documented, not captured" in the PR body.
- **An unknown or missing `notification_type` stays quiet.** It is never read as a question and never dropped silently. The type and the time go to `<git-common-dir>/crew/notify/unrecognised.log`, one line each, capped at 200 lines, so a type Claude Code adds later shows up there. Accepted as risk: a new question type is missed until someone reads the log or `notify.questionTypes` names it.
- **"One ping per waiting episode" needs a reply signal the hook does not receive.** The `Notification` hook fires on the prompt, not on the answer. The episode is therefore keyed on `session_id` + `prompt_id`: the first question ping of a prompt sends, later question pings with the same `session_id` and `prompt_id` are the same episode and stay quiet, and a new `prompt_id` (the owner replied and Claude went on) opens a new episode. Where `prompt_id` is missing the episode key falls back to `session_id` + the transcript's last assistant `uuid`, and where that is unreadable too, to the fingerprint dedupe alone (6h window). Accepted as risk: two different AskUserQuestions inside one prompt with no reply between them (Claude cannot do that without an answer, so it is not expected).
- **The transcript may be unreadable or empty.** Then the line carries the payload's `message` alone and a stderr note; the ping still sends. A transcript over 16 MiB is read from its tail (last 256 KiB) only.
- **The redaction filter is new.** No `redact` helper exists in `plugin/crew/hooks/scripts` (`git grep -i redact origin/main -- plugin/crew/hooks/scripts` is empty), so `crew_notify.py` defines `redact(text)`: replaces the value of every environment variable whose name contains `TOKEN`, `SECRET`, `PASSWORD`, `PASS` or `KEY` (when at least 8 characters long), Telegram bot tokens (`\d{6,}:[A-Za-z0-9_-]{30,}`), `Bearer <token>`, and `sk-`, `ghp_`, `github_pat_`, `xox[abp]-` and `AKIA` prefixed strings with `[redacted]`. The same function runs over the transcript excerpt, the payload `message`, and every line written to the state directory. Accepted as risk: it is a deny-list; the message and excerpt caps (280 and 200 characters) bound what a miss can leak.
- **A repo `provider: "none"` shadows a global provider.** Decided here: an explicit repo `"none"` is a deliberate opt-out and wins. The repo template default becomes `null`, so new repos inherit the global block. An existing repo keeps its `"none"`, and `crew_notify.py config` prints that the repo overrides a global provider. This repo's untracked `.crew/config.json` no longer holds `"none"`: at the split it names `telegram` with `events: ["gate", "waiting"]` (Evidence), so no edit to it is needed, and the legacy mapping below is what keeps its pings working.
- **The example chat id.** The notify skill's config on this machine still holds `-1001234567890`. The fallback treats that exact value as unset, so no send goes to a chat that does not exist.
- **Legacy event names.** A config naming `gate` reads it as `deploy`, and `waiting` as `question`. `phase`, `review` and `done` read as `blocker`, which is reserved until T-0060 and sends nothing here. `crew_notify.py config` prints one notice line per legacy name, and the hook run prints it to stderr. Nothing is dropped silently. The owner's live `["gate", "waiting"]` becomes `["deploy", "question"]`, which is the whole of this ticket's vocabulary.
- **The subject words.** `Question`, `Needs permission`, `Promotion passed` and `Deploy FAILED` (owner, 2026-09-26, the later decision). They live in one `SUBJECTS` table in `crew_notify.py`, so a rename is one line and one test. The subject is plain ASCII and is not configurable.
