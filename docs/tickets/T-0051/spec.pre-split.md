# T-0051 crew notify, rebuilt: Telegram pings only for blockers, deployments and questions          status: spec   risk: high
## Intent
crew's notifier becomes one Python module, `crew_notify.py`, that sends exactly three kinds of message: `blocker` (a plan waiting on approval, a ticket out of review rounds with BLOCKs open, a lane that died, a Stop gate refusing again after the session's own retry), `deploy` (every `/crew:promote` result, a pass silent and a failure loud) and `question` (a permission prompt or an MCP elicitation, from the `Notification` hook filtered on `notification_type`). An idle "waiting" never pings, and the per-phase, per-review and per-ticket pings are retired.

The Telegram send path is ported from the notify skill (429 `retry_after`, about 1/s pacing, HTML escaping). A fingerprint dedupe with a re-alert window (default 6h) lives under `<git-common-dir>/crew/notify/` and advances only on a confirmed send. The config is read from the machine-global `notify` block with the repo layer overriding it, and the notify skill's `telegram` block fills a missing token env or chat id read-only. `notify.sh` and `notify.ps1` become thin wrappers that keep `event_claim.py`'s one-sender election.
## Exclusions
- Outbound only. Nothing reads from Telegram, nothing carries a reply back into a session, and approvals stay a typed `/crew:approve`. No inline keyboards, no `getUpdates`, no daemon.
- No new hook registration. The `Notification` entries in `hooks.json` change their arguments; no event gains an entry. Every hook path exits 0: this ticket blocks nothing.
- No dependency on the notify skill being installed. `tg.py`'s logic is copied into crew, not imported, and `skills/notify/**` is not edited (no bump of that entry).
- No live Teams test is claimed. The Teams branch is kept and tested only against a local HTTP server.
- No stalled-lane detection. The `lane` reason exists in the CLI vocabulary, but T-0049 (in-flight markers and their TTL) and T-0029 (waves) wire their callers. No stall timeout is invented here.
- No wave-level approval batch. A batch covers one `/crew:autopilot` run (T-0004's one ticket). T-0029 and T-0024 reuse `blocker --reason approval` with several ids once they land.
- No ping for infrastructure refusals of the Stop gates (no python, no temp file, lock failures). Those paths have no working python to send with. Only the verification-failed refusal of `verify-gate` and the verdict refusal of `completion_audit.py` are counted.
- No findings text, diffs, ticket bodies, file contents or secrets in any message. The token is read from an environment variable only.
- No change to `event_claim.py`'s election rules. `hook_once.py` is not used.

## Unknowns
- **The AskUserQuestion `notification_type` is not measured.** Nothing in the docs or the binary strings read above ties AskUserQuestion to a type. If its dialog goes through the tool-permission path, it arrives as `permission_prompt` (6 s after it opens). If not, it may send nothing. Resolved before implement by step 1's live capture: a throwaway `Notification` hook that appends each payload to a scratch file, in an interactive session that triggers an AskUserQuestion, a Bash permission prompt, an idle wait of more than 60 s, and an MCP elicitation if a server offering one is available. The spec's type set is then confirmed or amended. Until then `question` is: `permission_prompt`, `worker_permission_prompt`, `elicitation_dialog`, `elicitation_url_dialog` and `agent_needs_input`. The list is overridable as `notify.questionTypes`, so a wrong guess costs a config line, not a release.
- **Measured vs documented.** `permission_prompt`, `idle_prompt`, `elicitation_dialog`, `elicitation_url_dialog` and `agent_needs_input` are documented and also read from the 2.1.283 binary. `worker_permission_prompt` is binary-only. None has been captured from a live hook payload yet. Step 1's capture records which ones it saw, and the rest stay labelled "documented, not captured" in the PR body.
- **An unknown or missing `notification_type` stays quiet.** It is never read as a question and never dropped silently. The type and the time go to `<git-common-dir>/crew/notify/unrecognised.log`, one line each, capped at 200 lines, so a type Claude Code adds later shows up there. Accepted as risk: a new question type is missed until someone reads the log or `notify.questionTypes` names it.
- **The stall timeout.** It needs T-0049's heartbeat TTL, and T-0049 is at `direction`. Deferred there (Exclusions).
- **Is `prompt_id` present on a Stop payload?** It is documented in the `Notification` example only. The Stop-refusal identity uses `prompt_id` when present, else a digest of the normalised payload, so the two Windows flavours count one refusal once. If two consecutive Stops were byte-identical with no `prompt_id`, they would count as one, and the ping would come one refusal late. Accepted as risk, and step 5 tests both shapes.
- **A repo `provider: "none"` shadows a global provider.** Decided here: an explicit repo `"none"` is a deliberate opt-out and wins. The repo template default becomes `null`, so new repos inherit the global block. An existing repo keeps its `"none"`, and `crew_notify.py config` prints that the repo overrides a global provider. This repo's untracked `.crew/config.json` holds `"none"`, so the owner either edits it to `null` or accepts the opt-out. Named in the PR body.
- **The example chat id.** The notify skill's config on this machine still holds `-1001234567890`. The fallback treats that exact value as unset, so no send goes to a chat that does not exist.
- **Legacy event names.** A config naming `phase`, `review` or `done` reads them as `blocker`, `gate` as `deploy`, and `waiting` as `question`. `crew_notify.py config` prints one notice line per legacy name, and the hook run prints it to stderr. Nothing is dropped silently.
- **Codex is out until 2026-10-01**, so the review may be same-family. Accepted as risk and announced.
