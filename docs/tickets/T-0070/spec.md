# T-0070 inert settings are loud, /crew:status --approvals lists only what needs you, a no-op /crew:approve says so, machine-level autopilot preferences          status: spec   risk: high
## Intent
A crew setting that the installed crew does not act on is named visibly. SessionStart, `/crew:status` and `crew_autopilot.py settings` each print one line naming the key, what it would do and the ticket that brings it, so a setting is never silently inert again. `/crew:status --approvals` prints only the tickets whose approval is actually missing or stale, as ready-to-paste `/crew:approve <id>` lines. A `/crew:approve` that would record nothing new says "already approved for plan <sha> - nothing changed" rather than recording it again. Every rule has a must-warn and a must-stay-quiet test, and a test proves the no-op message never hides a stale or unaccepted receipt.

Added 2026-09-27 (owner, via a choice dialog: "Add to T-0070"): the machine-global file `~/.claude/crew/config.json` may set eight autopilot preferences, `autopilot.approval`, `questions`, `mode`, `maxPhases`, `maxLanes`, `maxTicketsPerRun`, `reviewPolicy` and `ship`, plus `route.enabled`. The repo file still overrides each one by precedence. Today `filter_global` drops the whole `autopilot` and `route` blocks, and `--check-global` calls them IGNORED. After this change they pass the filter and the writer, and a key whose implementing ticket has not landed is reported as pending that ticket (named with the layer that set it), never as ignored. When the ticket lands and the key enters `crew_state.AUTOPILOT_DEFAULTS`, the key joins `default_global_config()` with no further edit, and the owner's global value takes effect. `autopilot.deploy`, the whole `scope` block and the whole `emergency` block stay repo-only. A global value for any of them is refused by the writer and dropped by the reader, as today, but it is now also named in the same inert line with the reason, so it is no longer silently ignored.

**Deploy rule (chosen): `autopilot.deploy` is repo-only.** No global value, alone or combined, grants or widens deploy. The machine owner's consent to an unattended deploy is T-0009's ratcheted `guards.deployWorkflow` (both layers, the narrower wins; T-0009 is approved, not landed, and T-0045 depends on it, so no deploy can run before that consent exists). T-0045, the ticket that implements `autopilot.deploy`, already decided to read the key repo over defaults and to add "no second authority layer". A both-layers-agree ratchet on `autopilot.deploy` would be exactly that second layer. It would also make every repo's opt-in also need a global edit, and it would guard nothing that `deployWorkflow` does not already guard. Rejected: the `environments.prodUnattended`-style ratchet.

**route.enabled (chosen): allow it globally.** Plain-text lifecycle routing is how the person types, not a fact about a checkout. T-0023, which implements it, already declares it global-settable (T-0023 spec `:9`, and `T-0023-build` adds `route` to both templates). Until T-0023 lands the key is inert, and the line names it with T-0023 rather than as ignored.
