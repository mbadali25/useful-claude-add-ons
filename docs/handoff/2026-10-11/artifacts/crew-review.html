Crew 1.2.0 Review

Two independent evaluators, Claude Opus 5.5 and Codex gpt-6-luna, both at high effort, read the plugin, its tests and ten weeks of real use. A third agent mapped the field as it stands in October 2026. This page brings the three together and ends with a phased plan for fixing what they found.

Subject crew 1.2.0 at origin/main c25ef990 Evidence ~400 tickets, 572 PRs, 220 review rounds Field 27 tools, primary sources
VERDICT · STRONG CORE, OVERGROWN, LEAKING AT THE EDGES
  • Best governance core in the field. No other tool combines all four: write permission tied to a hash of the approved spec, a scope guard on writes, environment-aware cloud and Terraform guards, and review by a different model family with a ledger of every round. About 2,650 sabotage mutations prove the guards fail when they should. Both evaluators agree on this.
  • Also the heaviest, by an order of magnitude. Production Python grew 3.3x in the 12 days after the 1.0 "make it smaller" redesign. The plugin has 38 commands, 33 skills and 234 config keys. Its complexity budget is spent, and the cost now shows up as defects every week.
  • The gates leak where it matters. On a clean main, the Stop gate takes about 55 s and still blocks. Shell-route scope checks read a ticket layout from before 1.0. Review quietly falls back to Claude reviewing Claude, which was the case for 32% of rounds. The tracker drifted by about 100 tickets.
  • The field moved. Claude Code now ships an auto-mode guard classifier, Workflows and ultrareview, and OpenAI ships an official Codex review plugin with its own Stop gate. Cross-model review is no longer unique to crew. What still sets crew apart is that its guards are deterministic and tested, and that it binds approval to a specific spec.
  • The fix: keep the gates and the evidence discipline. Stop the five leaks, make review cheaper, put state under code, and cut the surface by about half. Hold back new features until main is green.

Where crew stands

Each dimension is scored 1 to 5 by both evaluators, where 5 is best in the field. For cost, 5 means lightest. The dashed ring marks the best score any other tool earned on that dimension in the Opus table.

Opus 5.5 Codex gpt-6-luna Best other tool (Opus)

Where they disagree. On verification, Codex gave 5 because it judged the design, while Opus gave 3 because it measured the gate blocking a clean tree. Codex ran no tests, so the measured score is the one to trust. On portability, Codex gave 1 (Claude Code only) and Opus gave 3 (bash plus PowerShell parity). Both readings hold, because they measure different kinds of portability.

Against the field

Crew wins the columns that need code: spec discipline, safety and review. It loses the ones that need restraint: UX, cost and maturity. The platforms (Cursor, Codex, Devin, Factory) win on runtime isolation. A guard that inspects command text is a seatbelt, while an operating-system sandbox is a wall. Crew needs both and should say so.

What changed in the field since September

Cross-model review went mainstream

OpenAI's official codex-plugin-cc (33.9k stars) adds /codex:review, an adversarial review and a Stop-hook review gate inside Claude Code. The September comparison missed it.

The platform now blocks infra actions

Claude Code's auto mode, the default since v2.1.283, blocks prod deploys, IaC destroy, force push, IAM grants and unapproved merges by default. That overlaps crew's cloud-guard and promote-gate, but the platform uses a model to decide, while crew uses tested rules.

Review got deeper and cheaper to buy

/code-review ultra reproduces every finding before it reports it. Managed review reads a REVIEW.md that caps nitpicks and stops re-review loops.

Parallelism is native now

Claude Code Workflows run 16 agents at a time. Agent teams, Cursor Projects and Kiro background workflows also exist. Crew's own wave/lane runtime duplicates this.

Heavy frameworks are thinning out

Roo Code is archived, ccpm and SuperClaude have been idle since March, and wshobson/commands is archived. The leaders, superpowers (296k stars), Spec Kit (141k) and OpenSpec (71k), are light and portable.

Users' recurring complaints

Ceremony on small tasks, tiring markdown review, startup token overhead, overlap with native features, and review loops that drain usage. Crew shows all five.

Review as a protocol

Review follows a fixed procedure. It works from a bundle that includes the working tree, splits large diffs without truncating them, and gives a script-derived CLEAN / FINDINGS / INCOMPLETE verdict. It refuses the author's model family, and rounds are reserved before launch.

Weaknesses

Ordered by how much each one hurts day to day. I checked three of these by hand against origin/main: the scope reader, the hard-coded Claude fallback and the quickstart contradiction.

Critical · verified

Stop gate can't pass on its own main

On a clean main it takes about 55 s, defers 7 rules as "permanently over budget" and exits 2. The priced rules total 1,810 s against a 60 s budget. A gate that blocks because checks didn't run, rather than because they failed, trains you to ignore it. You see it on every turn here.

scope_report.py still parses the pre-1.0 - touch: lines in .work/tickets/<id>.md. Crew 1.0 writes <id>/spec.md ## Touch instead. The check is also report-only (|| true). Writes made with sed -i, cat > or python -c escape Touch.

What's missing

Proof that it pays off

  • There are no outcome evals comparing escaped defects, rounds, tokens and hours against plain Claude Code with /code-review.
  • No per-ticket token or cost telemetry.
  • No second user has completed /crew:init.

Gates in the right place

  • The full verify map should be a required CI check, with Stop running only a fast check on what changed.
  • Tests should be picked by the import graph, which graphify already has.
  • Reviewer findings should be checked before they cost a round.

State owned by code

  • Merges should move tickets and cards automatically.
  • Ids and versions should be allocated by code, not prose.
  • A GitHub Issues adapter, then Linear.

Use the platform

  • Lanes should run on Claude Code Workflows instead of a custom wave runtime.
  • Crew should layer on the auto-mode classifier rather than duplicate it.
  • Standards should be exported to REVIEW.md, the AGENTS.md review rules and BUGBOT.md.
The plan

How we fix it

The plan has four phases, in order. Each item says what to change, roughly how, which files it touches, and how we'll know it's done. Effort is per lane: S is under a day, M is 2 to 5 days, L is 1 to 3 weeks. Feature work stays frozen until Phase 1 is done and main has been green for a week.

Phase 1 · Stop the leaks

this week · 5 items · all S or M

Make the gates you already have tell the truth, so a red result means something is broken.

1.1
Hermetic tests, then a green mainS

Merge PR #545 (L-0704). Then add an autouse fixture to conftest.py that points HOME, XDG_*, CLAUDE_CONFIG_DIR and CLAUDE_PROJECT_DIR at tmp_path, and a meta-test that fails any test opening the real home directory. Quarantine timing flakes, each with a named owner.

plugin/crew/tests/conftest.py · test_crew_autopilot_status.py · test_review_checks.py:2261

The Stop hook stops failing on this machine's config, and main's pytest-crew is green for 7 days.

1.2
Make the Stop gate fit its budgetM

At Stop, run only rules mapped to files changed since the marker that fit in stopBudgetSeconds. Never exit 2 just because rules were deferred. Rules that never fit become a required CI check and a precondition for /crew:done, which reads the CI receipt. When zero rules ran, say so, and don't write the verified marker.

verify-gate.sh · verify_record.py · verify_fingerprint.py · commands/done.md · .github/workflows/verify-gate.yml · .crew/verify.json

Phase 2 · Make review cheaper

weeks 2–3 · target mean rounds 3.1 → under 2

Most findings belong to classes we already know about, and the biggest predictor of rounds is diff size. Catch the known classes with tools and keep diffs small.

2.1
Split by size at approvalS

Refuse /crew:approve when a plan projects more than about 300 production lines, or when it mixes a parser, guard or state machine with other work. Route those to /crew:split. Tickets under 150 lines averaged 2.19 rounds; tickets of 600 to 1,500 lines averaged 4.85.

commands/approve.md · crew_ticket.py · crew_autopilot_split.py · skills/crew-plan/SKILL.md

No approved plan is over the threshold unless it carries an owner waiver.

2.2
Turn known finding classes into lintM

Ship ruff and semgrep rules for the recurring classes: U+2028 in line protocols, unquoted CLAUDE_PLUGIN_ROOT, symlink or FIFO opens, duplicate-key JSON, bare executables, and tests with no failing control. A round can't be reserved until they pass.

review_checks.py · .crew/standards.md · new plugin/crew/lint/ · review_ledger.py

First-round findings in known classes fall by half.

2.3
Verify findings, carry dispositionsM

Borrow two ideas from ultrareview and REVIEW.md. First, reproduce or refute each finding before it costs a round. Second, feed the previous round's accepted and rejected findings into the next prompt, with a convergence rule ("after round 1, no new nitpicks").

review_run.py · review_prompt.py · recurring_findings.py · commands/review.md

Round 2 and later contain only regressions or unresolved findings.

2.4
One review budget per ticketS

Count rounds across successor plans. Resetting the count takes a named owner decision, recorded in the ledger.

review_ledger.py · commands/review.md · commands/status.md

The advertised cap matches the ledger.

2.5
Export standards to PR-side reviewersS

Generate REVIEW.md, an AGENTS.md "Code Review Rules" block and .cursor/BUGBOT.md from .crew/standards.md, with a freshness check like the code map's.

crew_docs_check.py · skills/crew-standards/ · commands/init.md · crew_freshness.py

Every reviewer, crew's or not, checks the same list.

Phase 3 · Put state and safety in code

weeks 3–5

Stop relying on session prose for anything another session or a merge can make wrong.

3.1

Add crew_tracker.py reconcile. It reads merged PRs and moves INDEX rows and cards, applying the rules used in today's manual pass: the merge must reach main and the PR must complete the ticket. Run it from /crew:done, SessionStart (rate-limited) and a CI job on main. Add a GitHub Issues adapter.

3.2
Release-time version bumpsM

Bump the version once per release, computed from changed plugin paths, instead of claiming and "burning" numbers per PR. Keep the drift check. Move code map, graph and diagram refreshes into the release job.

3.3
Require a sandbox for unattended runsS

autopilot run and wave refuse to start unless Claude Code's sandbox or a devcontainer is detected, or both config layers opt out. The docs say plainly that crew's guard is a seatbelt and the sandbox is the wall.

3.4
Memory-aware lane governorM

Cap the number of lanes based on cgroup or /proc/meminfo. Run heavy suites under systemd-run --scope -p MemoryMax= on Linux and a job object on Windows. This replaces the memory notes and the host wrapper.

crew_wave.py · crew_autopilot.py · crew_shell.py · commands/autopilot.md

No more OOMs from lanes, and no hand-set concurrency limit.

3.5
State hygieneS

Clean up stale .autoclear-sent-*, .handoff-requested-* and retired .pm-pulse* files at SessionStart. Replace ADR 0003, which still defends 54 agents, with a new ADR. Re-anchor the crew code map, which is about 200 versions behind.

Phase 4 · Shrink it and prove it

weeks 5–9 · the large one

Cut the surface by about half, lean on what the platform now does natively, and publish evidence that crew is worth its overhead.

The core crew plugin keeps the lifecycle, guards, review and verify. Opt-in plugins hold the rest: crew-trackers (sdp/jira/obsidian/change), crew-autopilot, crew-promote (promote/emergency/gate), crew-cloud and crew-docs (diagram/runbook/reference/survey/graph). That takes commands from 38 to about 20 and deletes the removal stubs.

Do not cut

  • Spec-hash approval and the Touch write guard
  • Review receipts and the CLEAN / FINDINGS / INCOMPLETE protocol
  • The fail-closed rule that an unknown is never a pass
  • Sabotage mutation tests. Reorganise them, but keep them
  • The cloud guard's environment model
  • The commit-anchored code map

Cut or fold

  • Delete the removal stubs ticket, upgrade and work
  • Fold config-setup into config, help into status and split into plan
  • Drop the PostToolUse context hook on every Read/Edit unless measurement shows it helps
  • Drop the Notification hook and the typed auto-clear resume, which overlap native features
  • Archive the CHANGELOG at each minor version, and drop the 30-line provenance headers

Decisions only you can make

  1. Feature freeze. Hold all new crew features until Phase 1 lands and main stays green for a week. Recommended: yes.
  2. Who crew is for. Is crew for you alone, or for a second user? The answer decides whether Phase 4.1 (the split) and the onboarding work come first or last.
  3. Windows parity scope. Keep full PowerShell twins, or move to the single-dispatch launcher (4.4) so Windows support costs about one file.
  4. Ticket filing. I can file these 20 items as tickets (next free C-0070 / L-0709) with Kanban cards, grouped by phase. Phase 1 can then run as parallel lanes.
