## Constraints that shape the options

- The anchor-state result must not go INTO the generated file. `rule_digest` (`plugin/crew/hooks/scripts/crew_instructions.py:105`) hashes the note, so the rule is a pure function of the codemap; a rule that embedded "behind" would change on every commit that touches a cited path, and `rules --check` (run in CI via `.crew/verify.json:268`, and in this repo where several anchors lag HEAD at any time) would go red with no codemap change - losing the fixpoint `plugin/crew/hooks/scripts/crew_freshness.py:229` `_moved_since` exists to keep.
- The warning must use the same classifier as the session-start line (`crew_context.anchor_state`), or the two surfaces will disagree about which subsystems need re-check - the exact confusion the report describes.
- An unknown must stay its own value (this repo's recurring bug): `unresolvable` and `unknown` (no git HEAD) are reported as such, never folded into "current" or silence.

## Options

1. **Warn, never change the exit code (recommended).** `rules` and `rules --check` print one line per subsystem whose `anchor_state` is `behind` or `unresolvable` (and one `could not tell` line when there is no HEAD), naming the anchor and the re-check command, after the write/drift lines. The generated files are unchanged, and exit codes keep today's meaning (1 = drift only). The `up to date` summary no longer reads as an all-clear when anchors lag: it says the rules match the code map and how many maps need re-check. `/crew:migrate` (preview and apply) and `/crew:onboard` step 6 tell the operator what those lines mean and what to do (refresh with `/crew:onboard --refresh <subsystem>`, or generate knowingly and record it). Tradeoff: advisory only, so an operator can still ignore it - but it is the same advisory weight session-start already carries, and it is on the one command the report says was silent.
2. **Refuse to write from a stale note unless overridden** (`rules` exits non-zero and skips those subsystems, `--allow-stale` to proceed). Tradeoff: blocks `/crew:migrate` apply on any repo whose maps lag, which is most repos mid-life, for a condition that "behind" explicitly does not mean "wrong" (`plugin/crew/hooks/scripts/crew_freshness.py:374` docstring: re-check, not re-derive). Skipping a subsystem also drops its rule entirely, which is worse guidance than a rule with an old anchor. Extending the refusal to `--check` would turn CI red on every lagging anchor. Rejected.
3. **Docs only.** Migrate and onboard tell the operator to read the session-start "Anchors to re-check" line before generating. Tradeoff: no code signal at the moment of generation, which is the report's actual complaint; relies on the operator having a fresh session-start line. Rejected as insufficient on its own; its doc half is folded into option 1.

## Recommendation

Option 1. It closes the reported gap (generation from lagging anchors is now said out loud, on the same classification session-start uses), keeps the generated artifacts and the CI check deterministic, and does not block migrate on a condition that means "re-check", not "wrong". YAGNI: no new flag, no strict mode, no change to what the rule files contain.

Scope note (not a file list; that is the spec's): this is a `plugin/crew/` change, so the project CLAUDE.md doc rule applies - every document describing `rules`, `/crew:migrate` and `/crew:onboard` step 6 is updated in the same PR, and the crew version is bumped one patch past origin/main at push time.
