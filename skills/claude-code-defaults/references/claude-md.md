# CLAUDE.md, rules, and auto memory

## What goes where

| Scope | Path | For |
|---|---|---|
| Managed policy | `/Library/Application Support/ClaudeCode/CLAUDE.md` (macOS), `/etc/claude-code/CLAUDE.md` (Linux/WSL), `C:\Program Files\ClaudeCode\CLAUDE.md` (Windows) | Org-wide standards; can't be excluded by users |
| User | `~/.claude/CLAUDE.md`, `~/.claude/rules/*.md` | Personal preferences across all projects |
| Project | `./CLAUDE.md` or `./.claude/CLAUDE.md`, `.claude/rules/*.md` | Team-shared, committed |
| Local | `./CLAUDE.local.md` | Personal, this repo only; gitignore it |

Loading order runs broadest → most specific, and files are **concatenated, not overridden** — so a project instruction lands in context after a user instruction rather than replacing it. Claude Code walks up the directory tree from the launch directory and loads every `CLAUDE.md` and `CLAUDE.local.md` it finds along the way. Files in *sub*directories load lazily, when Claude reads a file in that directory.

`/init` generates a starting project CLAUDE.md from the codebase, and suggests improvements rather than overwriting if one already exists. It also folds in existing Cursor (`.cursor/rules/`, `.cursorrules`) and Copilot (`.github/copilot-instructions.md`) rules. Setting `CLAUDE_CODE_NEW_INIT=1` enables an interactive multi-phase flow that asks what to set up, explores with a subagent, and shows a reviewable proposal before writing anything.

## Writing instructions that actually get followed

CLAUDE.md is delivered as context, not as enforced configuration. Compliance is strong but not guaranteed, and it degrades with length, vagueness, and contradiction. Three things drive adherence:

**Specificity.** Concrete enough to verify:

- "Use 2-space indentation" — not "format code properly"
- "Run `npm test` before saying a task is done" — not "test your changes"
- "API handlers live in `src/api/handlers/`" — not "keep files organized"

**Structure.** Headers and bullets, grouped by topic. Claude scans structure the way a reader does; a wall of prose is worse than the same content in six labeled sections.

**Brevity.** Target under 200 lines. Every line is in the context window for every session, competing with the actual work. Splitting into `@` imports helps organization but *doesn't* reduce context — imported files load at launch too. Only path-scoped rules actually defer loading.

Cut anything Claude can derive from the codebase itself: directory listings, dependency inventories, generic architecture overviews. Keep the things it can't infer — pitfalls, rationale, conventions that differ from tool defaults, the reason that weird module exists. (`/doctor` proposes exactly this kind of trim for a checked-in CLAUDE.md.)

Block-level HTML comments (`<!-- note to maintainers -->`) are stripped before injection, so they cost no tokens — a good place for notes to humans.

### A good starting shape for a project file

```markdown
# <Project name>

## Commands
- Install: `pnpm install`
- Test: `pnpm test` (single file: `pnpm test path/to/file.test.ts`)
- Lint: `pnpm lint --fix`
- Dev server: `pnpm dev` (port 3000)

## Conventions
- TypeScript strict mode; no `any` without a comment explaining why.
- 2-space indent, single quotes, trailing commas.
- Tests live beside the code as `*.test.ts`.

## Architecture notes
- `src/api/` handlers are thin; business logic goes in `src/services/`.
- Database access only through `src/db/client.ts` — never import `pg` directly.

## Before you call it done
- Run `pnpm lint` and the tests for the files you touched.
- Don't edit `src/generated/**` — it's regenerated by `pnpm codegen`.
```

Note what this does *not* contain: no file tree, no dependency list, no restating of things any competent reader would infer from the repo.

## When to add something

Add to CLAUDE.md when:

- Claude makes the same mistake a second time
- A code review catches something Claude should have known about this codebase
- You type the same correction you typed last session
- A new teammate would need the same context

If the entry is a multi-step procedure, or only matters in one part of the tree, it belongs in a skill or a path-scoped rule instead — not in the file that loads every session.

## `.claude/rules/`

One topic per file, discovered recursively:

```
.claude/
├── CLAUDE.md
└── rules/
    ├── testing.md
    ├── api-design.md
    └── frontend/styling.md
```

Rules without frontmatter load at launch with the same priority as `.claude/CLAUDE.md`. Rules **with** a `paths` field load only when Claude works with matching files — this is the main tool for keeping context lean in a big repo:

```markdown
---
paths:
  - "src/api/**/*.ts"
  - "tests/**/*.test.{ts,tsx}"
---

# API rules

- Every endpoint validates input before touching the database.
- Use the standard error envelope from `src/api/errors.ts`.
```

Glob patterns: `**/*.ts`, `src/**/*`, `*.md`, `src/components/*.tsx`. Brace expansion works and shares a budget of 1,000 expanded patterns per rule, so don't nest many groups. A `[` that can't be read as a bracket expression makes that one pattern match nothing (escape it as `\[`).

User-level rules go in `~/.claude/rules/` and load before project rules, giving project rules higher priority. `.claude/rules/` supports symlinks, so a shared company rule set can be linked into many repos:

```bash
ln -s ~/company-standards/security.md .claude/rules/security.md
```

## Imports

`@path/to/file` inside a CLAUDE.md expands that file into context at launch. Relative paths resolve against the file containing the import, not the working directory. Max depth is four hops. Imports are skipped inside code spans and fenced blocks, so `` `@README` `` stays literal while `@README` imports.

Sharing personal instructions across git worktrees is the main real use — a gitignored `CLAUDE.local.md` only exists in the worktree where it was created, so import from home instead:

```markdown
# Individual preferences
- @~/.claude/my-project-instructions.md
```

The first time a *project* file imports something resolving outside the working directory, Claude Code shows an approval dialog listing the files — protection against imports someone else commits. Declining disables them permanently for that project. User-scope imports load without a dialog.

## AGENTS.md

Claude Code reads `CLAUDE.md`, not `AGENTS.md`. For a repo that already has one, import it so both tools stay in sync:

```markdown
@AGENTS.md

## Claude Code
Use plan mode for changes under `src/billing/`.
```

A symlink (`ln -s AGENTS.md CLAUDE.md`) works if no Claude-specific content is needed — but on Windows that needs Administrator or Developer Mode, so prefer the import.

## Auto memory

Separate system: Claude writes its own notes to `~/.claude/projects/<project>/memory/`, keyed off the git repo (so all worktrees share one directory). It's machine-local and never synced.

- `MEMORY.md` is the index, and **only its first 200 lines or 25KB load** into each session. Topic files (`debugging.md`, etc.) are read on demand.
- On by default. Toggle in-session with `/memory`, or set `"autoMemoryEnabled": false` (per-project or user-wide). `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` does it via environment.
- Relocate with `"autoMemoryDirectory": "~/my-memory-dir"` (absolute or `~/`-prefixed). From project/local settings this only takes effect after accepting the workspace trust dialog.
- It's all plain markdown — readable, editable, deletable. `/memory` browses it.

When someone says "Claude remembered something wrong", this is usually where it lives, not CLAUDE.md.

## Troubleshooting "it's ignoring my CLAUDE.md"

Work through these in order:

1. **Did it load?** Run `/context` and check the **Memory files** list. If the file isn't there, Claude cannot see it — wrong location, or excluded. `/memory` opens the files it knows about.
2. **Is it in a loaded location?** Files in subdirectories below the launch directory load lazily, not at startup.
3. **Is it specific enough?** Vague instructions are the single most common cause. Rewrite to something verifiable.
4. **Is something contradicting it?** Two files giving different guidance on the same behavior means Claude may pick either. Check ancestor CLAUDE.md files and `.claude/rules/`. In a monorepo, `claudeMdExcludes` skips other teams' files:
   ```json
   { "claudeMdExcludes": ["**/monorepo/other-team/**"] }
   ```
5. **Does it need to be enforced rather than requested?** If it must happen at a specific moment — before every commit, after each edit — it's a hook, not an instruction.
6. **Was it lost after `/compact`?** The project-root CLAUDE.md is re-read from disk and re-injected after compaction. Nested files aren't; they reload the next time Claude reads a file in that directory. Anything given only in conversation is gone — that's the signal it should be written down.

The `InstructionsLoaded` hook logs exactly which instruction files loaded, when, and why. It's the fastest way to debug path-scoped rules.
