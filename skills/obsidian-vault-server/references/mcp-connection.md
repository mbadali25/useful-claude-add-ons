# Connecting Claude to the vault

The `obsidian-local-rest-api` plugin serves an MCP endpoint at `/mcp/` alongside its
REST API. No separate MCP server process runs.

## The connection model

```
Claude Code  --http-->  127.0.0.1:27123  ==SSH tunnel==>  server 127.0.0.1:27123
                        (workstation)                      (Obsidian plugin)
```

The plugin listens on the server's loopback only. The tunnel is what makes it
reachable and also what encrypts it. Nothing is published to the network.

## Register it

```bash
# terminal 1 - leave running
ssh -N -L 27123:127.0.0.1:27123 you@server

# terminal 2
claude mcp add --transport http obsidian-server http://127.0.0.1:27123/mcp/ \
  --header "Authorization: Bearer <api-key>"
claude mcp list
```

Claude Desktop, if the build supports remote HTTP MCP servers — add to
`claude_desktop_config.json` and restart:

```json
{
  "mcpServers": {
    "obsidian-server": {
      "type": "http",
      "url": "http://127.0.0.1:27123/mcp/",
      "headers": { "Authorization": "Bearer <api-key>" }
    }
  }
}
```

If it does not, bridge with [`mcp-remote`](https://www.npmjs.com/package/mcp-remote).
The tunnel must be up **before** Claude Desktop starts, or the server shows as
failed until you restart it.

## Why plain HTTP rather than the plugin's HTTPS

The HTTPS listener on 27124 uses a **self-signed certificate**. Most MCP clients
reject it and Claude Code has no per-server "skip TLS verification" switch. Rather
than push a self-signed cert into every workstation trust store, enable the plugin's
HTTP listener, bind it to loopback, and let SSH encrypt. End to end the traffic is
still encrypted — SSH is doing it instead of TLS.

To use TLS anyway, through the tunnel:

```bash
curl -k -o obsidian.crt https://127.0.0.1:27124/obsidian-local-rest-api.crt
# trust it locally, then point Claude at https://127.0.0.1:27124/mcp/
```

## The API key

Lives in `<vault>/.obsidian/plugins/obsidian-local-rest-api/data.json`, generated by
the plugin on first load. Print it with `obsidian-vault-server.sh apikey`.

It grants **full read and write** on the vault — create, edit, delete, search. Treat
it as a credential:

- Never commit it, never paste it into a ticket.
- It sits in the workstation's Claude MCP config in cleartext.
- **Never let it sync.** Enabling *"Installed community plugins"* in Obsidian Sync
  replicates `data.json` to every device on the account. Leave that toggle off.
- Rotate: delete `apiKey` from `data.json`, restart the container, re-run `finalize`,
  re-register with Claude.

## Verifying

```bash
# unauthenticated status - returns versions and whether the request carried a key
curl -s http://127.0.0.1:27123/ | jq .

# authenticated
curl -s -H "Authorization: Bearer <api-key>" http://127.0.0.1:27123/vault/ | jq .
```

If the root answers but authenticated calls 401, the key is stale — re-read it.

## What Claude can do once connected

Same capability set over REST and MCP: list vault files, read a note, create or
replace, append, patch relative to a heading or block reference, delete, search the
vault, open a note in the UI, run Obsidian commands. Everything lands in the vault
directory and is picked up by Sync like any other change.
